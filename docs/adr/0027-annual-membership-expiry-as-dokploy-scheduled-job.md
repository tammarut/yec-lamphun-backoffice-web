# Annual membership expiry runs as an expiry-keyed, idempotent command executed by a Dokploy scheduled job inside the app container

Once a year, from 1 December (the start of the **Renewal Season**, when the chamber collects renewals at the annual general meeting), every live `ACTIVE` member whose **Membership Expiry** precedes the **Membership Year** the season opens — or who has no `expires_at` at all — is moved to `EXPIRED` by the **Annual Membership Expiry**: a repo-owned Bun script entry point (`scripts/annual-membership-expiry.ts`) that resolves a members-module use-case from the DI container, is bundled into the production image by the Dockerfile, and is executed by a Dokploy *Application* Schedule Job (cron `1 0 1 12 *`, `docker exec` in the running container, per-run output in Dokploy's job history). This is the **first Member Status transition outside the Membership Renewal lifecycle** — a new transition class, recorded here rather than silently breaking the CONTEXT.md invariant that every status write flows through a renewal flow. This ADR records the design settled in the 2026-10-26 grilling session; implementation lands via the spec + tracer tickets cut from it.

## Why

### 1. Expiry-keyed, not "every ACTIVE member"
`expires_at` is stamped with the next calendar year's end at member creation, at every Manual Renewal Submission, and at every approving Renewal Review (ADR-0016), so a member who renews (or joins) in November 2026 already holds `2027-12-31T23:59:59.999Z`. An unconditional run would expire them three weeks after they paid, and — worse — would make re-running the job destructive: everyone who renewed after 1 December would be re-expired by a second run, so the job could never be retried or run manually. Keying the predicate on the expiry (`expires_at < $boundary`) makes the job **idempotent**: a renewed member carries next year's expiry and is untouchable until the following season, so re-running on any date is a no-op for them. A NULL `expires_at` is deliberately NOT matched (2026-10-26 PR-review ruling, superseding this ADR's original "NULL counts as expired" stance): a missing expiry is a legacy data anomaly to correct out-of-band, not to auto-expire — the job only flips members holding a real, past expiry instant.

### 2. The boundary comes from the run date, so cadence is an ops knob, not code
The job computes its boundary as a pure function of `now`: read the Bangkok year and month (the ADR-0019 dual-pinning precedent — SQL writes and JS reads must agree on timezone), take the season year as `month === 12 ? year + 1 : year`, and return UTC midnight of its 1 January. UTC is deliberate: Membership Expiry instants are stamped with UTC setters, so a "Bangkok end-of-year" boundary would miss every row by seven hours. With this rule the script is correct on *any* day of the year (December runs flip the ending year's members; January–November runs only catch overdue stragglers), which means the chosen once-a-year cron (`1 0 1 12 *` — fires 00:01 UTC / 07:01 Bangkok on 1 December, same date either way) is purely a Dokploy setting: moving to daily for self-healing later requires no code change, and a missed run is recovered by simply running the command again. No "did it already run?" marker, settings row, or audit table exists or is needed — the run trace is one structured LogTape JSON line (`run_at`, `boundary`, `expired_count`, `duration_ms`) plus exit code 0/1, which Dokploy's job history captures.

### 3. Dokploy schedule job over an endpoint, an embedded scheduler, or external cron
The repo has exactly one auth mechanism (`withAuth`, a staff session cookie — unusable from cron), so an API endpoint would require inventing a second, shared-secret auth path and would expose a publicly reachable bulk-mutating URL that nothing else in the app needs; the trigger would also live outside the container (host crontab, Cloudflare/port path). An embedded scheduler (croner started from `src/instrumentation.ts`) fires only if the web process happens to be alive at that minute, runs per-instance (local dev server and every Dokploy app would need env gating), hides the job inside a request-serving process, and adds a dependency. A Dokploy *Application* Schedule Job (docs.dokploy.com/docs/core/schedule-jobs) `docker exec`s a command into the already-running app container: it inherits the container's env (`DATABASE_URL`) and Bun runtime for free, needs no new auth surface, and every execution leaves a log entry in Dokploy. The one precondition it adds — the target container must be running — is trivially true for a web app. Rejected for the record: GitHub Actions `schedule` (30–60 min delays, auto-disabled after 60 days of repo inactivity, DB reachable from GitHub IPs), pg_cron (business logic outside the repo, extension install on the DB host), and a Go cron service (a second image and deploy pipeline for one UPDATE — pure overhead at this scale).

### 4. Target status `EXPIRED`, never `PENDING_RENEWAL`
The machinery around renewal already treats `EXPIRED` as the renewable state: the admin picker of the manual renewal flow searches `EXPIRED` members only, the public create-renewal endpoint refuses `PENDING_RENEWAL` members with 409 (a status read as "a live PENDING_RENEWAL renewal exists"), and the Expired Membership List/worklist is keyed on `status = 'EXPIRED'`. Bulk-setting `PENDING_RENEWAL` would therefore lock every member out of renewing. `PENDING_RENEWAL` and `RESIGNED` members are never expired: the former are mid-review (their approving Renewal Review lands them on `ACTIVE` with a fresh Membership Expiry — already renewed), the latter are out of the lifecycle entirely.

### 5. The members module owns it; the cache-column contract is amended, not broken
The job writes `members.status` and nothing in `membership_renewals`, so under ADR-0024's one-repository-per-table rule it belongs to the members module (the renewals repo's ownership of member UPDATEs, ADR-0014/0018, is per renewal-flow transaction; this is not one). It touches `status` alone among the Renewal Cache Columns — `latest_renewal_status`, `expires_at`, and `renewal_successful_count` stay as they are (`expires_at` untouched keeps the historical record of when the membership ended; a later renewal re-stamps it). CONTEXT.md's Member Status, Renewal Cache Columns, and Status Badge entries are amended to name the Annual Membership Expiry as the one non-renewal writer, and the glossary gains the Annual Membership Expiry, Renewal Season, and Membership Year terms.

## Considered options

- **Repo script + Dokploy Application schedule job (chosen).** In-container execution inherits env/runtime/DI; no new endpoint, auth, or host-side trigger; run history in Dokploy; manual rehearsal/recovery is the same command in the container terminal (`--dry-run` for a count-only pass).
- **API endpoint + `CRON_SECRET` header auth + host crontab curl.** Rejected: a second auth mechanism and a public mutating URL for a job with no HTTP consumers; trigger outside the container adds a network path to reason about.
- **Embedded scheduler in `instrumentation.ts`.** Rejected: per-instance firing with env-gating burden, alive-at-that-minute fragility, scheduler hidden inside the web process, new dependency.
- **GitHub Actions `schedule`.** Rejected: unreliable timing, auto-disable on repo inactivity, DB exposure to GitHub IPs.
- **pg_cron.** Rejected: business logic outside the repo (no tests, no types), extension installation on the Postgres host.
- **Go cron service.** Rejected: a second image, registry, and deploy pipeline for one UPDATE statement.

## Consequences

- `EXPIRED` gains a second writer (the first date-driven one); every reader of `members.status` — dashboard counts, Renewal Stat, Expired Membership List, org-chart dots, member badges — keeps its existing semantics but sees the values swing on 1 December: total_active collapses, not-yet-renewed counts spike, org dots go gray. That visible flip is the intent.
- Committee members are expired like everyone else — no honorary/lifetime exemption concept exists; they remain on the org chart until `RESIGNED`, with gray dots until they renew.
- The missed-run failure mode is not silent in practice: at the general meeting the admin renewal picker (EXPIRED-only) comes up empty, and recovery is running the command in the Dokploy container terminal — safe on any date thanks to idempotency.
- The Dockerfile gains a builder-stage `bun build` of the script and a runner-stage `COPY`; the image gains the bundle at `/app/annual-membership-expiry.js`, beside the standalone `server.js` and owned by the non-root user (amended by OPS-01b, PR #111 — the source stays at `scripts/annual-membership-expiry.ts`, only the bundled artifact lands at the image root). Local `eslint`/`tsc` already cover a root `scripts/` directory. Implementation spike: RESOLVED by OPS-01b — `bun build --target=bun` bundles tsyringe decorators + `reflect-metadata` (`emitDecoratorMetadata`) correctly; the bundled script resolved the service from the DI container and completed a `--dry-run` inside the built image, so the fallback (constructing the service directly) was never needed.
- The affected count comes from `:many` + `RETURNING id` (rows returned = members expired) — the sqlc TS plugin emits no `:execrows` executor, so the ADR-0001 convention applies.
- Single-UPDATE atomicity needs no transaction wrapper; the Dokploy cron is evaluated in the host's clock (UTC) — re-verify in the Dokploy UI when configuring, and note the job requires the container to be running.
- Out of scope, deliberately: any coupling to `open_membership_renewal`, a persisted run marker or audit table, an admin "run now" button, notifications, and any change to the Membership Expiry formula. No API surface changes, so no Apidog work.
