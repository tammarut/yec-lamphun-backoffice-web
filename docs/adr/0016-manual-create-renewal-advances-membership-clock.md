# Manual create-renewal advances the membership clock; Membership Expiry is unified

`POST /api/v1/membership/renewals/manual` is a **staff-only** sibling of the public create-renewal endpoint. It is wrapped in `withAuth` (missing/invalid `session_id` → `401`), unlike the public route's optional cookie (ADR-0015). A manual submission is always an Admin Submission (`APPROVED` / `ACTIVE`), but — unlike a plain Admin Submission on the public route — it **also advances the member's membership clock**: it bumps `renewal_successful_count` by one and sets `expires_at` to the Membership Expiry. We also unified the `expires_at` rule: both member creation and manual renewal now use one shared formula (end of next calendar year).

## Why

### 1. Staff-only, with a 401
The public route's optional-cookie model serves *members themselves* filing a renewal (ADR-0015). The manual endpoint serves a different actor — backoffice staff recording an in-person payment — and the spec marks `session_id` required. Reusing the public route's soft (no-401) check would let an unauthenticated caller file a renewal that instantly approves *and* advances the membership clock (sets `expires_at`, bumps the count). That is a privileged write, so it must reject with `401` when the session is absent or invalid, exactly like the members CRUD routes. `withAuth` is the established wrapper for exactly this; the manual route uses it.

### 2. The clock-advancing write belongs here
ADR-0015 explicitly deferred `expires_at` and `renewal_successful_count` to "the future review/approve API," leaving the public create-renewal flow writing only two of the four Renewal Cache Columns (`status`, `latest_renewal_status`). This manual endpoint is the staff-side slice of that future API: when staff record a paid renewal in the backoffice, the membership should be extended *now*, not queued for review. So the manual repository method writes all four cache columns (a dedicated `UpdateMemberOnManualRenewal` query), while the public route is untouched and ADR-0015's deferral stands for it.

### 3. Membership Expiry is one rule, shared
The OpenAPI spec's pseudocode contradicted itself on the `expires_at` formula (the two examples said end of *current* year; the pseudocode heading said end of *next* year, with a buggy double-increment). We confirmed with the domain owner that the intended value is **end of the next calendar year** (`${currentYear+1}-12-31T23:59:59`). The pre-existing member-creation formula (`now + 1 calendar year, end of that day`) was then unified to the *same* rule, so a member is always aligned to a calendar-year cycle — whether created fresh or renewed. To respect AGENTS.md §1 (no `members` ↔ `membership-renewals` TS imports) and §2A (shared contracts in `src/modules/shared/`), the single formula lives as a pure function `computeMembershipExpiry` in `src/modules/shared/membership/`; both aggregates (`Member`, `MembershipRenewal`) delegate to it.

### 4. A new use-case + repo method, not a flag on `CreateRenewalService`
The two flows share a great deal (the status pre-check read, the error vocabulary, the aggregate's status-pair rule, the INSERT query, `withAuth`/`mapError`). But they differ in two load-bearing ways: (a) the auth contract — public-optional vs staff-required; and (b) the cache-column write — 2 columns vs 4. Folding these into a flag on the existing service (`isManual`/`mode`) would push manual-specific concerns (the clock-advancing write, the literal-status query) into the public path's branch, and the public repo method's `createRenewal` would gain a conditional UPDATE. A dedicated `CreateManualRenewalService` + `createManualRenewal` repo method keeps the two contracts cleanly separated while *reusing* the genuinely shared pieces (the pre-check read `getMemberStatusForRenewal`, the error classes re-exported from the sibling use-case folder, the aggregate class via a second factory `MembershipRenewal.createManual`, the private `doInsertRenewal` helper).

## Considered options

- **New staff-only use-case + repo method; shared expiry util (chosen).** Clean separation of the two contracts; maximum reuse of the pre-check, errors, aggregate, INSERT, and (now) the expiry formula. ADR-0015's deferral is partially superseded for the manual path only.
- **Extend `CreateRenewalService` with a `mode`/`isManual` flag.** Rejected: couples the public path to manual-only concerns, and forces the public `createRenewal` repo method to conditionally pick a different UPDATE query. The two flows have genuinely different write contracts (2 vs 4 columns).
- **`withOptionalAuth` middleware variant.** Rejected: the manual route is *not* optional-auth — it must 401. Reusing the public route's inline soft check (invalid cookie → public-style `PENDING_REVIEW`) contradicts the spec's required `session_id` and the privileged nature of the clock-advancing write.
- **Two expiry formulas kept distinct (creation = now+1yr end-of-day; renewal = end of next year).** Rejected at the domain owner's direction: unify to one calendar-year rule so the codebase has a single notion of membership tenure.
- **Expiry formula computed in SQL (`date_trunc`/`make_timestamptz`).** Rejected: diverges from the `Member.computeExpiry` precedent (TS-side), is harder to unit-test, and would mean the repo no longer takes `expires_at` as a param (muddying the aggregate's role as the source of the value).

## Consequences

- **Member-creation behavior changes.** A member created mid-2026 now gets `expires_at = 2027-12-31T23:59:59.999Z` instead of ~`2027-08-08T23:59:59`. This is accepted (calendar-year alignment is the business rule) and recorded in `CONTEXT.md` under **Membership Expiry**. The existing `member.test.ts` assertion was strengthened to pin the exact instant (the prior loose year/hours checks passed coincidentally under both formulas).
- The renewals module has a **second repository method** writing the `members` table (`createManualRenewal`, alongside `createRenewal`). Both own their own transaction; both reference the members schema for sqlc parsing only (symmetric with ADR-0014). The manual write is excluded from the partial unique index `idx_one_pending_renewal_per_member` (status is `APPROVED`, not `PENDING_REVIEW`), so it can never raise Postgres 23505 — its error type is just `DatabaseError`, and the only `PendingRenewalExistsError` on the manual path comes from the service pre-check (`member.status === PENDING_RENEWAL`).
- The shared `computeMembershipExpiry` util is the **third** place the membership clock is computed (joining `Member.create` and — now — `MembershipRenewal.createManual`), but it is the *only* place the formula is *defined*. It is a plain function, not a DI-registered service (no token/container entry), matching how other pure shared modules are organized.
- This **partially supersedes ADR-0015's "Known gap — no membership-period concept"**: the manual endpoint now writes `expires_at` and `renewal_successful_count`. The *full* gap (supersede-on-renew, a current-vs-historical renewal distinction, widening the unique index with a supersede step) remains open and still belongs to the future review/approve API. Do NOT "just widen the index" — a live `APPROVED` row blocking all future renewals would break the periodic-renewal business model.
- A manual double-submit still produces a duplicate `APPROVED` renewal row (same accepted gap as the public admin path, ADR-0015) — but unlike the public path, each manual submit *does* bump `renewal_successful_count` and re-stamp `expires_at`, so the member data stays correct even if the renewal rows accumulate.
